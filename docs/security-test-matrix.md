# CLPR security test matrix

The catalogue of attack vectors CLPR has considered, what defends against each, and where that
defence is asserted. This is the canonical list: `test/security/` implements it, and a test's name
carries its row id (`test_X1_nonOwner_reverts` asserts row X1).

Row ids are **append-only** — they are referenced from test names, so a row is retired by
marking it, never by renumbering.

Classification: `E` executable/new · `E*` executable/already asserted elsewhere · `D`
documented-only · `N` no defence exists · `deferred` the vector exists only under the
`ChannelSyncData` model (#400), so the row keeps its id until that lands.

Citations name a **file and a symbol**, never a line — a symbol survives edits and is greppable.
Slot numbers and byte lengths are quoted together with the constant that proves them.

66 vectors: 14 verifier, 12 bundle, 12 messaging, 14 channel, 14 access control.

## 1. Verifier attacks

The errors in `ClprTypes` are **service-layer** errors; verifiers almost never use them and declare
their own instead. The only `ClprTypes` error any verifier raises is `VerifyFailed(string)`
(HieroVerifier only). `MockAvalancheVerifier` performs **no** cryptographic verification — its
`verifyBundle` is `pure` and returns the `QueueMetadata` and payloads decoded from the proof bytes
as-is (`ClprProtobuf.decodeBundleContent`) — and
is excluded from the compliance gate by the `Mock` prefix rule in `VerifierComplianceCoverage`.

| # | Vector | Why it matters | Defence | Class | Suite / notes |
| --- | --- | --- | --- | --- | --- |
| V1 | Forged state proof: fabricate a proof that a peer message exists | The verifier is the entire trust boundary; a forged proof injects arbitrary cross-ledger messages | Per family. | V12 | Untested execution-branch guard | An SSZ branch check nobody exercises may not work | `EthMainnetVerifier` declares `ExecutionBranchInvalid()` and raises it on both the bundle and config-manifest paths; no test in the repository asserts it | `E` | Forge — write it |

## 2. Bundle attacks

Entry chain: `ClprService.submitBundle` → `BundleLogic.submitBundle` (`nonReentrant onlyService
whenEnabled`) → `BundleLib.processBundle` → `_validateAndPrepare` / `_applyBundle`.

`BundleLib` reads local state from `_channels[channelId]`, and the verifier returns
`(QueueMetadata, messagePayloads, newTrustAnchor, newTrustAnchorId, newEndpointManifest)`. A bundle's
last message is the peer's `nextMessageId - 1`, and `sentRunningHash` is its proven running hash.

| # | Vector | Why it matters | Defence | Class | Suite / notes |
| --- | --- | --- | --- | --- | --- |
| B1 | No-progress bundle DoS: resubmit a bundle that advances nothing | Cheap griefing; wasted gas, event spam, log noise for relayers | `BundleLib._checkBundleProgress` reverts the BundleLib-local `NoProgress()` unless one of five criteria advances: `nextMessageId` exceeds our `receivedMessageId + 1`; a new trust anchor; a higher manifest version; the peer's `receivedMessageId` exceeds our `ackedMessageId`; or `_stepStatus` yields a status transition under a look-ahead `effectiveAcked` | `E` | Forge. Existing: `BundleLib_Progress.t.sol`, `BundleLib_StateMachine.t.sol` |
| B2 | Rate-limit bypass: flood `submitBundle` | Unbounded submission rate | **None.** `ClprBundleRateLimitExceeded` is **never raised**, and its own doc-comment cites a `maxBundlesPerSec` throttle that exists nowhere in the tree. No window, counter, or timestamp state exists in `ClprServiceStorage`, and `ClprTypes.Throttles` has no rate field. Only `NoProgress` and gas cost limit a flood | `N` | File issue. `test/invariants/README.md` describes a rate limiter that does not exist — correct the doc |
| B3 | Running-hash forgery: deliver payloads that do not match the peer's proven chain | Breaks the cross-ledger integrity chain; enables message injection. Only the peer's queue-head `sentRunningHash` is proven, so this check is what protects every payload in the bundle | `BundleLib._validateAndPrepare` Step 5 seeds `computedHash` from `channel.receivedRunningHash` (forced to zero when nothing has been received), chains `sha256(prev ‖ sha256(payload))` over the **new suffix only** — leading duplicates are already folded into the seed — and compares against the verifier-proven `QueueMetadata.sentRunningHash` → `ClprRunningHashMismatch`. Not skipped for a payload-free bundle: the seed itself must equal the proven hash | `E` | Forge. Existing: `BundleLib_Validation.t.sol`, `BundleLogic_ErrorHandling.t.sol`, `BundleLib_PartialBundle.t.sol` |
| B4 | Bundle replay / rewind: resubmit a processed bundle, or claim more new messages than payloads carried | Double-dispatch of inbound messages | `BundleLib._validateAndPrepare` Step 4 computes `newMessageCount = nextMessageId - (receivedMessageId + 1)` and raises `ClprReplayDetected` when it is negative or exceeds `messagePayloads.length`, so a payload-free bundle must claim exactly `receivedMessageId + 1`. A count of exactly zero is left to `_checkBundleProgress`, which runs earlier. `messageStartIndex` is the tolerated leading-duplicate window that makes prefix bundles legal | `E` | Forge. Existing: `BundleLib_Replay.t.sol`, `BundleLib_PartialBundle.t.sol` |
| B5 | Message-ID sequencing: gaps, reordering, or replies out of order | Application-visible reordering; silent message loss | Ids are assigned in lockstep in `_dispatchMessages`, so gaps are structurally impossible. Reply ordering is pre-scanned in `_checkResponseOrdering`; a violation on a CLOSING channel reverts `ClprBundleVerificationFailed`, on ACTIVE it moves the channel to PAUSED and returns without dispatching, and on PAUSED it is a no-op. Auto-resume back to ACTIVE is a later step | `E` | Forge. **Note:** `ClprInvalidMessageId` is *not* the bundle-path error; it is redaction-only (`MessagingLogic.redactMessage`). A pause is persisted to `_channels`, and the peer's verifier proves that status word directly (`ClprEvmBundleVerifier._channelMetadataSlots`). Existing: `BundleLib_ResponseOrdering.t.sol`, `BundleLogic_Ordering.t.sol` |
| B6 | Ack forgery: ack a message never sent, or move the ack backwards | Frees queue slots and quota that were never consumed; corrupts in-flight accounting | The ack **is** the peer's proven `QueueMetadata.receivedMessageId`. `_validateAndPrepare` Step 6 rejects a backwards move and an ack at or beyond `channel.nextMessageId` → `ClprAckVerificationFailed`. The value itself is state-proven at the verifier (V7), so it cannot be fabricated | `E` | Forge. Existing: `BundleLib_Validation.t.sol` covers both branches; `BundleLogic_ErrorHandling.t.sol` |
| B7 | Oversized bundle: exhaust gas or memory via blob, message count, or payload size | Block-level DoS; unprocessable channel | `proofBytes.length > maxSyncBytes` → `BundleTooLarge()`, checked in Step 2 **before** the verifier call. `messagePayloads.length > maxMessagesPerBundle` → `TooManyMessages()` and per-payload `> maxMessagePayloadBytes` → `ClprPayloadTooLarge`, both **after** the verifier call. Peer endpoints are truncated rather than rejected via `ClprTypes.truncateEndpoints`. Defaults come from `ClprConfig.defaultThrottles` | `E` | Forge, including the at-limit boundary. **Note** `TooManyMessages` is checked *after* `_checkBundleProgress`, so a bundle that is both oversized and no-progress reports `NoProgress` — assert the intended error, not just "reverts". Existing: `BundleLib_Validation.t.sol`, `BundleLogic_RateLimiting.t.sol` |
| B8 | Malformed protobuf: unknown wire field, bad oneof variant, empty payload, wrong wire type | Decoder confusion; divergent interpretation across implementations | Three errors abort the whole bundle. `ClprUnknownWireField(fieldNumber)` from `ClprProtobuf` is caught and re-thrown byte-for-byte on the DATA and CONTROL paths (`BundleLib._revertWith`), and propagates directly on the REPLY path. `ClprBundleVerificationFailedOneOfVariant` from `decodeControlMessage`. `ClprBundleVerificationFailedEmptyPayload` from `getMessageType`, which is called *outside* the try/catch. On the CONTROL path the decoder's own `ClprProtobufHelpers.TruncatedInput` and `VarintOverflow` abort it too. The wire type of a *known* field is not checked: `decodeDataMessage`, `decodeReplyMessage` and `decodeControlMessage` read each field under its expected type, and `ClprEvmBundleVerifier._decodeBundleContent` skips field-2 entries that are not length-delimited. Every *other* DATA decode failure degrades instead to `BundleParseFailed` plus an `APPLICATION_ERROR` reply | `E` + `N` | Forge + Vitest (real RPC error surface); the unchecked wire type is `N`. Existing: `BundleLib_ParseFailure.t.sol`, `BundleLib_ApplicationErrors.t.sol`, `BundleLogic_Configuration.t.sol` |
| B9 | Unauthorized endpoint submits a bundle | — | **Not a vector.** `submitBundle` is permissionless *by design*; `onlyService` asserts the delegatecall context, not the caller, and `msg.sender` is used only as `bundleSubmitter` — the charge and slash-proceeds recipient. No authorization decision reads it | `N` | Doc fix. `docs/bundle-flow.md` and `test/invariants/README.md` both claim an `isRegistered[msg.sender]` gate that does not exist. Existing: `BundleLib_Payment.t.sol` pays an arbitrary pranked submitter |
| B10 | Decode-side unbounded input via `BundleDecodeHelper` | A trampoline could pass hostile input through unchecked | `BundleDecodeHelper` is three `external pure` pass-throughs with **no** bounds of its own; bounds live in `ClprProtobuf`. Its only security role is being an external call boundary so `BundleLib` can `try/catch` a decode | `D` | Interface-level. **Gap worth noting**: `decodeReply` is invoked **without** try/catch, so on the REPLY path the isolation the helper exists to provide is not actually used |
| B11 | Dead error surface | Unraisable errors imply defences that are absent | `ClprBundleRateLimitExceeded` and `BundleLib.EmptyBundle` are declared and never raised. An empty bundle is rejected by `NoProgress` instead, or accepted when it carries a fresh ack | `N` | File issue: raise or delete |
| B12 | Status-transition forgery: drive the channel to CLOSING or CLOSED from the peer side | The peer's proven status (`QueueMetadata.state`) gates the drain sequence and, at CLOSED, the channel's end of life | Peer-driven transitions go through one function, `BundleLib._stepStatus`, shared with `_checkBundleProgress` and `_applyStateMachine` so progress and application cannot disagree. Transitions are monotonic, at most three hops, one event per hop, and gated on `_allDataAcked` / `_allOutboundAcked`. The peer's status is state-proven at the verifier (V7) | `E` | Forge. Existing: `BundleLib_StateMachine.t.sol` (exhaustive combination coverage), `BundleLogic_ClosingLogic.t.sol` |

## 4. Channel lifecycle attacks

| # | Vector | Why it matters | Defence | Class | Suite / notes |
| --- | --- | --- | --- | --- | --- |
| C1 | Commitment-reveal bypass: complete a channel without a matching commit | Opens a channel to an unagreed peer key | `ChannelLogic.completeChannel` requires `keccak256(abi.encodePacked(channelId, pubKey))` to be present in `_pendingCommitments` → `ClprCommitmentMismatch`. One-shot: `_createChannel` consumes it | `E` | Forge. Existing: `ChannelLogic.t.sol` |
| C2 | Commitment squatting: pre-register garbage under an observed `channelId` | `_channelIdToCommitment` is first-write-wins, so `closeChannel`'s pending-cleanup path purges the attacker's entry rather than the real one. The legitimate reveal still succeeds, being keyed on the commitment hash | **None.** `registerChannel` is permissionless with no relationship check between `channelId` and `commitment`, acknowledged in an in-code comment | `N` | File issue. No test exists |
| C3 | Reveal-signature forgery / replay onto another deployment | Would let anyone open a channel as an arbitrary peer operator | `ECDSA._verifySignature`: the 64-byte pubkey length is enforced in `completeChannel` and again in the library; the digest is `keccak256(channelId ‖ address(this))`, EIP-191 prefixed; `ecrecover == 0` is rejected; and the recovered address must equal `address(uint160(uint256(keccak256(pubKey))))`, so signer identity derives from the *committed* pubkey bytes | `E` | Forge. Existing: `ChannelLogic.t.sol`, whose `test_completeChannel_revealSignature_isDomainSeparated` is the authoritative router-binding replay test |
| C4 | Cross-chain signature replay | A fork or identically-addressed deployment with the same `_config.chainId` string accepts the same reveal signature | **No `block.chainid` and no EIP-712 domain separator anywhere** (grepping `block.chainid` over `src/` finds nothing). Binding is `channelId ‖ address(this)` only. `ClprInvalidChainId` fires solely on an empty chain string in `_sortChains`, and nothing checks `_config.chainId` against the real chain | `N` | File issue — the highest-value finding in this catalogue |
| C5 | Duplicate channel; channel-count exhaustion | Duplicate state records; cap-exhaustion griefing | `completeChannel` checks the `maxChannels` cap (`0` meaning unlimited) → `ClprTooManyChannels`, then `_channelExists` → `ClprChannelAlreadyExists`. `BundleLib` additionally rejects a PENDING record at bundle intake → `ClprInvalidChannelStatus` | `E` | Forge.
